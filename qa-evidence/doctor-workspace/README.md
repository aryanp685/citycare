The previous implementation commit `06b7db2` is not the current HEAD. ## Implemented and observed

- Real DB-derived doctor dashboard stats/schedule; connected-patient search and cards; read-only profile, with admin approval explicitly not described as official NMC/IMR verification; doctor activity sourced from the existing audit ledger.
- Verified doctor can request summary, last three visits or full record for treatment or second opinion **only for an existing appointment-linked patient**. Request is seven days, patient/guardian inbox notification is in-app only, no access is conferred. It uses the existing consent table/partial unique index, per-user rate-limit bucket, a transaction, audit and notification; concurrent duplicate requests tested. Patient may select their scope and grants seven days from approval. Deny stores DENIED; a specific `consentId` prevents accidentally approving a later request from a stale UI. Legacy patient-initiated grants without a request ID and legacy revoke calls remain supported.
- Patient access page displays scope, purpose, expiry and status, with card layout and review/deny/revoke controls. Expired pending/approved rows render expired. The appointment shortcut now leads to the access screen rather than guessing request status.
- The server-rendered doctor patient page checks approval and a pre-existing relationship before exposing identifiers and records its separate print read in the ledger. `PatientWorkspace` clears stale data after network/server failure. **These do not solve in-flight revocation races.**

## Blockers and limitations

1. **P0 — revocation race:** consent is checked before subsequent clinical reads/writes; an already-in-flight operation can continue after revocation. This affects existing record, print, encounter and document paths and needs transactional design plus actual concurrency tests. New requests after completed revocation were tested, not the race.
2. **P0 review — scoped write:** encounter safety checks load full patient sections under narrower consent; whether returned alerts leak hidden facts must be assessed and tested.
3. Patient registration and linking without an appointment, clinic and staff scoping, more comprehensive profile editing and official credential review are not implemented. Request purpose is limited to two existing enum values; patient approval uses seven days. There is no new versioned consent model, separate rejection delivery or external messaging.
4. Encounter form is pre-existing and directly creates records; it lacks mandatory explicit confirmation, draft/finalized/amended/cancelled lifecycle and clinical signing. No prescription signing claim.
5. Doctor/patient new controls are English and lack a bundled Devanagari font; A-3.2 remains **NOT ACCEPTED**. Broader responsive/keyboard/accessibility and translation review are incomplete. The dashboard does not cover every metric requested, and the directory caps results at 100 rather than paginating.
6. System-font selection, offline behavior, consent UI error/retry, encounter save and simultaneous clinician actions need wider tests. Historical synthetic DB/account fixtures were not real patient data.

The consolidated register retains all 51 original `D-` IDs in its appended crosswalk (the document describes 40 but actually lists 51), plus DW findings. Status labels are conservative and many unrelated issues remain unverified; this iteration did not independently close them all. No commit, push, PR, merge or deploy.
