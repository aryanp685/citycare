# CI HTTP E2E repair — synthetic verification

The GitHub Actions job for PR #14 failed in its HTTP E2E step; its detailed hosted log was unavailable from this sandbox, so the exact hosted failure list was not directly inspected. A local reproduction used an isolated loopback PostgreSQL 18.6 cluster, a newly bootstrapped UTF-8 synthetic database, throwaway keys, and a built app. The CI workflow uses PostgreSQL 17, so local results are not a substitute for the hosted check.

Before repair the local suite recorded 398 passes and 8 failures: three legacy document-authorization assertions expected 403 instead of the existing deliberately generic 404; terms were prerendered without the runtime retention policy; PostgreSQL 18 reported `restrict_violation` 23001 rather than the test's required 23503 in two FK probes; two least-privilege tests hard-coded port 5432 instead of this isolated server's port. The repair preserves generic 404 denial, adds equivalence checks for unavailable vs revoked documents, forces runtime rendering of the terms notice, and verifies both supported FK error codes plus row preservation. The least-privilege tests now preserve the configured local DB host and port and still require permission-denied failures and no seed rows.

With a second freshly bootstrapped synthetic database, the repaired E2E suite reported **407 passed, 0 failed**. The terms build was made with DB variables unset and preview prebuild reported zero DB work. `browser.mjs` checked the built app at 375px with separate demo/pilot runtime policy settings; the demo displayed the seven-day clause, while the pilot did not falsely assert demo auto-erasure. Both sampled pages had no document-level horizontal overflow. Chromium 153 ran with `--no-sandbox`; this is neither full accessibility nor cross-browser verification. One initial browser harness expectation wrongly assumed that a non-demo deployment would display the public-demo paragraph; the expectation was corrected to check that it does not make the demo erasure claim.

No production data, migrations or deployment were invoked by this repair. This does not resolve the known consent/revocation synchronization and scope safety issues: DW-P0-01/02 remain OPEN / NOT ACCEPTED.
