# DW-P0 acceptance test specification — proposed, NOT EXECUTED

Static test design only; no security correctness or runtime claim. DW-P0-01 and DW-P0-02 remain **OPEN / NOT ACCEPTED**; all 48 approvals PENDING. `AUTHORIZATION_BOUNDARY_DESIGN.md`, `LOCK_ORDER_ANALYSIS.md` Proposal V1 and `CLINICAL_SCOPE_MATRIX.md` Retrieval contract V1 are conditional proposals, not current behavior or approval. Resolve owner/privacy, clinical and technical choices before asserting a particular policy result; where the documented option is fail-closed, test that exact approved option. Release owner separately decides go/no-go.

## Harness and evidence requirements

Use only an explicitly authorized, isolated, disposable PostgreSQL database and synthetic users/patients/documents/canaries; apply migrations as separately authorized, never connect to shared/production data or credentials. Capture schema/migration and application revision, DB version/isolation/timezone, test configuration and non-PHI trace, without signing secrets or raw sensitive payloads. Run actual routes/SSR against this DB with at least two independently acquired PostgreSQL connections and independent requests/transactions, not nested calls on one connection. Use deterministic, test-only barriers/hooks at: after gates/row locks, after authorization and fresh-clock recheck, before content retrieval, before ledger, before COMMIT, after COMMIT/before response, and COMMIT acknowledgment. Barriers must not introduce earlier-class locks or bypass normal authorization. Confirm overlap and actual blocking via transaction/connection identities plus `pg_stat_activity`/`pg_locks` or equivalent isolated instrumentation, not sleep alone. Bounded waits avoid hung tests; release barriers in cleanup. Use actual `clock_timestamp()` with a configured short synthetic future expiry and synchronize after it passes; do not fake transaction-start `now()` as the post-wait clock. Never set the system/production clock.

For each race record actor, connection ID, start, gate/lock acquired, consent/status recheck and authorization linearization point, blocked edge, commit/rollback, actual output and final DB state/audit, with timestamps and monotonic event sequence. Repeat both orderings and enough iterations under varied scheduling, include contention and multi-key cases. Assert results, not merely absence of exceptions. A test is **inconclusive**, not passing, if overlap, blocking, fault injection, outcome or audit durability cannot be established. Mocks, unit scope functions, sequential HTTP tests and prior doctor-workspace QA are useful but are not concurrency proof. Test exact actual deployed SQL constraints/FKs/triggers in the disposable environment; static proposal does not establish their compatibility.

## Concurrency and authorization scenarios

| ID | Independent-session sequence and required assertion |
|---|---|
| R1 | For **each** doctor record JSON, encounter POST, SSR/print (including Flight), link mint and document GET: A reaches valid authorization and holds K/C/D (plus H) while B attempts patient revoke. Observe B blocked until A commits or rolls back; A may finish if authorized first; B then commits. A fresh operation begun after B commit must deny without protected payload. Verify actual DB and distinct audits. An already materialized/delivered response cannot be recalled. |
| R2 | Reverse R1: B takes exclusive pair/consent gate and commits revoke before A locks/rechecks. A must deny, including a URL minted earlier; no stale session or prelookup authorizes. Repeat with appointment auto-revoke, patient cancel if it revokes, and replacement/deny/lapse transitions where applicable. Verify cancellation/status and revoke atomicity; failed status change does not partially revoke. |
| R3 | Race doctor suspension/rejection with each R1 surface in both orders. A authorized first may finish while B waits on Doctor gate/row; after B commits every new doctor surface denies, including valid signed URL. | R4 | Initially no consent: A takes shared pair gate, B tries grant/request insert; assert no false row lock, no ghost access, B waits and A denies. | R8 | Patient erasure and doctor erasure, each versus grant creation, revoke, document link/download, clinical write and appointment change; start erasure first and last. ## Scope, safety and leak oracle

Seed distinct synthetic canary strings/IDs in each field and in allowed and forbidden rows: active/inactive allergies/conditions/medications, DRAFT notes, multiple dated/tied encounters, linked/unlinked labs and observations, inner-joined and null prescription, deleted/other-patient document, each document blob, demographic/guardian fields, and foreign patient. Include more than 50 encounters, 200 labs, 1000 observations, 50 prescriptions/documents to detect limit-before-filter changes; test tie IDs, null timestamps and Unicode/case condition matching. Use controlled allowed facts separately from forbidden canaries. For each approved scope and invalid config compare exact rows/columns/order/caps to V1; assert no clinical values are returned to the application for filtered-out rows (instrument the query boundary), while documenting DB predicate evaluation of condition candidates. Test alternatives such as unlinked inclusion/exclusion, NULL N and selected-document support only against the approved choice. Unknown scopes, null/empty conditions, malformed N, foreign/deleted selection and missing policy deny; never broaden. Test the patient-ownership branch independently to avoid accidental restriction or bypass.

For every valid and denied scope, inspect response status, headers, JSON/422 warnings, errors and validation, SSR HTML, hydration/Flight chunks, browser print content, links, decrypted bytes, generated artifacts, Alert/Notification rows, audit metadata, app/server/DB logs and tracing. A forbidden canary, value-derived warning, identifying count, title or byte sequence anywhere is failure, not just an empty record section. Pair canary tests with negative controls showing allowed data survives intact, to avoid a vacuous pass from an empty response. For encounter creation test allowed-input allergy/lab/follow-up warnings, overrides, insufficient clinical inputs and malformed scope: no hidden inputs passed to rules, no hidden-derived 422, alert, audit, drug names or notification; generic deny when prerequisites are unapproved or absent. A rule test is not a clinical-safety review.

## Document and fault semantics

- Test mint versus revoke/suspension and GET versus revoke/suspension in both R1/R2 orders. A link is UID/document/expiry bound and not sufficient authority; verify wrong UID, signature, expiry, document, patient and deleted blob uniformly deny with no title/MIME/blob preauthorization. Scope replacement and reuse follow approved grant-binding/replay policy. Each successful mint and authorized download has its own minimal event; mint is not proof of bytes delivered and authorized-buffer audit is not a delivery receipt. Patient path uses independent ownership.
- Inject document read/decryption failures, signature errors, missing/corrupt blob, response construction failure, consent/query failure, and audit outage before COMMIT. Verify no protected payload or persisted partial clinical mutation; successful protected audit failure is fail-closed. A denial audit must be committed separately per approved policy; audit outage never makes denial allow, and operational alert is non-PHI. Test SQL logs/exception paths as leak surfaces.
- Force PostgreSQL `40P01`, lock and statement timeout, and transaction rollback at each stage. Assert full rollback, bounded waits, generic error and no unauthorized output; retry only whole, known-rolled-back idempotent operations with fresh authorization. Assert lock release. Do not accept automatic retry of unknown non-idempotent writes/mints.
- Drop connection before COMMIT and at COMMIT acknowledgment independently using an isolated fault proxy/harness. Before COMMIT verify rollback; during/after COMMIT may be committed or rolled back: require explicit `outcome_unknown`, no success/rollback assertion, no automatic replay, no bytes/link released, then reconcile from durable state/audit using an approved identifier if available. If no reliable reconciliation exists, mark this acceptance item blocked, not passed. Verify no duplicate write/notice/audit and distinguish a fresh authorized read retry.
- Verify rendering/buffering and delivery boundary: transaction commits only after approved complete representation or controlled endpoint has prepared it, no clinical streaming/Flight chunk before commit; HTTP transmission may complete after revoke. Browser-cached/downloaded/printed copies remain outside server recall. If framework cannot ensure pre-commit buffering, fail implementation feasibility and do not accept.
