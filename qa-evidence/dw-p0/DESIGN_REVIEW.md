Findings are code-inspection results, not a new exploit demonstration or a passing security test. ## 2. Linearization and locking — proposed contract

**Authorization instant:** after authenticating the actual viewer and starting a dedicated READ COMMITTED transaction, obtain a `FOR SHARE` row lock on the authoritative consent for exactly `(patientId, doctorId)`, re-read its committed status, scope, grant identity and expiry after any lock wait, obtain a fresh `clock_timestamp()` in a separate statement, and verify approved, unexpired, expected pair, scope and required verified-doctor status. The operation becomes authorized only when **all** checks have succeeded while the necessary locks remain held. A read/print/link/download creates its complete scoped DTO/bytes, including safe metadata and mandatory audit, on that same transaction client before commit; writes include safety evaluation, all mutations, alerts, notification and audit in it. No protected response or success can be sent before successful commit. A transaction failure rolls back and must return a generic failure, never a partially prepared protected response.

`FOR SHARE` conflicts with PostgreSQL's row locks for ordinary non-key `UPDATE` and `DELETE`; `FOR KEY SHARE` is insufficient. Concurrent protected operations can share a consent lock. Patient revoke performs a conditional `UPDATE` on that exact row and appends its receipt in the same transaction; if authorization holds a share lock, revoke waits, then commits after the operation has completed/committed or rolled back. If revoke wins, the waiting operation must see/recheck the changed row and deny. Do **not** rely on a pre-lock snapshot, a cached verdict, or a `WHERE status='APPROVED'` query alone to preserve denied/pending/revoked reasons. A failed or timed-out revoke has not committed: report failure, not success. Two revokes serialize; only the winner changes state and emits its success receipt; the other receives a closed/conflict result.

**Selection and absent rows:** `liveConsent` currently chooses latest `requestedAt` without a tie-break. Define deterministic authoritative selection, use an identifier-stable lock and re-read after waits; never fall back to an older approved grant when a newer request/terminal row exists. The unique partial index prevents simultaneous stored REQUESTED/APPROVED rows per pair, but does not by itself serialize absence, timestamps, expired stored-active rows, or writers that create terminal history. A missing row is never an authorization: deny without acquiring a fictitious row lock, even if a grant appears later. A concurrent new valid grant can authorize a *new* attempt only. If the implementation needs a stable pair snapshot for transitions/replacement, all pair creators, grantors, revokers, auto-revokers and emergency paths must use one transaction-scoped pair gate before row lookup (shared for readers, exclusive for mutations), including absence; the current request-only advisory key is **not** such a universal protocol. Use a domain-separated stable key; hash collisions may unnecessarily serialize, never grant access. Prove exact design against all writers before adopting it; no new table is assumed. Bulk erasure needs a patient/doctor-level gate that also excludes new grants while it enumerates, with deterministic pair ordering, or an equally rigorous alternative. Pair advisory locks alone are not enough if erasure misses a concurrently inserted pair.

**Doctor status:** record/encounter currently perform an unlocked `requireVerifiedDoctor`; document link/download do not. Proposed: lock and check the Doctor row `FOR SHARE` before consent for doctor clinical paths, including documents; verification rejection/suspension/anonymization updates must conflict. This strengthens enforcement and provides the same in-flight semantics as consent, subject to owner approval. `admin/emergencies/[id]/review` currently updates Consent **then** Doctor; reverse/refactor it before imposing Doctor → Consent ordering or it can deadlock. Session validity and patient status also need explicit threat-model review; do not silently claim session-revocation serialization.

**Ordering to prove, not yet established:** a candidate global order is stable account/patient and doctor erasure gates (in a single documented deterministic order), Doctor row if required, pair gate(s) sorted, Consent row(s) sorted, appointment/clinical/document rows, then ledger advisory lock last. Every code path and FK/trigger-acquired lock must be mapped before finalizing; pre-discovery reads may obtain IDs only, followed by identity/state revalidation under locks. Current appointment status locks appointment → ledger → consent; patient cancellation locks appointment → consent; booking inserts appointment → consent; erasure locks consent then clinical/appointment and later doctor/user; emergency review locks consent → doctor. These are concrete inversions or potential inversions for a naïve new order. Ledger `ledger_append` serializes on an advisory transaction lock, so consent → ledger versus ledger → consent forms a cycle. Reorder entire workflows, not just the visible append; sort multi-row locks and test FK/trigger interactions. PostgreSQL deadlock victim `40P01` and serialization/lock/statement timeout failures must roll back; return a safe retriable error without automatically replaying a non-idempotent write. Connection loss at COMMIT can yield an **unknown** outcome: don't assert rollback or blindly retry; reconcile by durable idempotency/evidence or communicate uncertainty. Existing `tx` does not retry, while non-transactional `poolQuery` retries some connection failures; keep protected queries on the transaction client.

**Expiry:** in READ COMMITTED, `now()` is fixed at transaction start; compare fresh DB `clock_timestamp()` **after** lock acquisition to `expiresAt` (UTC/naive timestamp convention explicitly pinned; test exact equality and timezone). Expiry is a derived denial when clock >= expiry, even if stored status is still APPROVED/REQUESTED. A previously authorized operation may finish after wall-clock expiry, just as with revocation; expiry itself does not wait or lock. Optionally persist `EXPIRED` under an exclusive lock and ledger a truthful lapse before replacement; preserve why it lapsed. Wall clock can move backwards: without durable lapse observation / trusted-clock assumptions an expired but still APPROVED row can appear valid again. Persisting observed expiry prevents revival after observation but cannot prove monotonicity through an unobserved clock rollback. Owner must choose trusted time/monitoring and durable-expiry semantics; do not claim stronger guarantees from `clock_timestamp()` alone.

**Response boundary:** a lock cannot recall bytes, browser state, a printed page, or a PDF already delivered. Construct all data and serialized/buffered output before commit; after commit only transmit that immutable result. Next server components may render/stream after a callback returns, so implementations must explicitly ensure no lazy protected reads or sensitive serialization run after release. Print button may print already delivered HTML after revocation; a new server-render after commit must deny. A 60-second signed link is only a bearer-like locator bound to a viewer; downloading separately reauthorizes. Network transfer can continue after commit; requiring revocation to wait for network completion would need a different explicitly approved protocol.

## 4. Scope isolation and leakage

Build an immutable scope plan from the **locked** grant before loading clinical sections. FULL_RECORD may query current full set. Existing `applyScope` contract is SUMMARY = active allergies, conditions and medications only; LAST_N = those safety facts + newest N encounters, linked prescriptions/labs/observations and currently unlinked labs/observations (and any nullable prescription links); SPECIFIC_CONDITION = safety facts + encounters matched by complaint/diagnosis and their linked rows; files hidden except FULL. SPECIFIC_DOCUMENTS currently falls to empty: the schema has a `documentIds` array, but the doctor scope filter and download authorization do not implement it. Condition matching uses empty-string `includes`, so a missing condition can match everything; fail closed. LAST_N defaults to 3 and existing section fetch limits/order (50/200/1000 etc.) affect behavior: explicitly specify selection/order/ties/limits and compare results before changing. Validate malformed N and missing/unknown scope fail closed. Whether unlinked readings and all safety facts are genuinely within each granted scope needs patient/clinical-owner confirmation; do not silently change the contract or widen it.

Implement parameterized SQL projections with patient and authorized encounter/document predicates **in the DB**, selecting only permitted rows/columns into the application; no unconditional `recordSections` before `applyScope`. For LAST_N select allowed encounter IDs first; linked reads use those IDs. For condition scope DB must evaluate the condition against candidate complaint/diagnosis fields to select matching rows: distinguish this predicate evaluation inside PostgreSQL from returning out-of-scope clinical values to app/rules; if the requirement prohibits even DB evaluation, current free-text model cannot meet it without a different approved model. Hide nonmatched rows/counts and cap/query-plan behavior; full noninterference against timing/database internals is not proven. Safety rules/digest receive only this scoped DTO plus doctor's proposed input. If a safe write requires facts not authorized by that scope, refuse with a generic need-for-broader-access response before clinical processing, not a false assurance that checks were comprehensive. Existing rules are limited and unreviewed; preserving them is not a clinical safety endorsement.

Check leakage in: safety 422 titles/messages/evidence and alert counts; validation/DB errors (`translatePgError` can expose messages, generic handler logs exceptions); digest abnormal labs and follow-up; `scopeNote` and status reasons; document title/checksum/mime/blob, filename, URLs and existence; patient demographics/ABHA and guardian; directory last-visit dates/appointment reason; stored alerts/notifications, audit `meta` including drugs/conflicts, denial logs and error logs; RSC HTML, React Flight payload, print CSS, client state, JSON serialization, headers and cache. Test that allowed information still has exact source values, and approved safety warnings still fire. Protect logs, audit and responses from out-of-scope values; patient-visible authorized audit can record minimal action/grant/scope without hidden clinical facts. Decide fail-closed auditing vs best-effort (currently link audit is swallowed). Denied attempts need a separate safely committed audit transaction or explicit atomic error-return pattern: throwing inside a tx after appending rolls the denial audit back.

**Negative evidence plan:** use synthetic unique canaries in each section, unrelated encounter, lab, observation, prescription, file title/content and hidden demographics; place canary in a fact that would trigger a detailed rule warning. For every scope and surface assert absence in entire status/body/headers/JSON/HTML/Flight/print, alerts, audit payload, logs and persisted notification; vary only hidden data and compare outputs (including counts) against a control. Instrument the transaction client/test adapter to capture SQL projections, parameters, result row IDs/column names and rule-engine inputs (not PHI) and assert forbidden rows/columns are never returned to application or rules. A mock SQL test alone is not enough: run this instrumentation against real PostgreSQL, include linked/unlinked and cross-patient fixtures, condition predicates, empty/malformed scope, and allowed-warning positive control. Document whether DB itself evaluates predicate fields, and avoid claiming absolute absence from planner/storage access.

## 5. Consent state machine and historical accuracy

- **PENDING** is UI terminology for stored `REQUESTED`; creation is not authorization. Patient approval transitions REQUESTED → APPROVED and records decision/time/scope; explicit patient denial transitions REQUESTED → DENIED and records `DENY_CONSENT`, never `REVOKE_CONSENT`. Direct patient grant can create APPROVED without a prior request; emergency is separately identified override, not a patient approval.
- APPROVED → REVOKED only on withdrawal/auto-revoke/erasure with truthful actor/reason and atomic event. A revoked approval does not become denied. A pending request cancellation needs an honest decision/cancellation representation; current legacy PATCH can label REQUESTED as REVOKED, and cancellation/emergency currently mark unexpired requests EXPIRED. Decide explicit cancellation semantics, not falsified expiry or revocation.
- REQUESTED/APPROVED → effective EXPIRED when DB clock reaches expiry; optional persisted EXPIRED transition must be serialized, distinguish prior state and record reason where needed. Denied/revoked terminal meaning takes precedence after expiry. Current `evaluateConsent` already checks revoked/denied before clock; explicit EXPIRED with a future expiry currently gets generic status denial. Normalize state presentation without inventing an approval or audit action.
- Terminal historical rows are not reused to represent a new grant: create a new row after terminal/lapse, retain old row and existing audit chain; approval of that pending row is a transition, not an overwritten previous grant. Approval may change scope from request; capture both meanings truthfully. Existing `approvedAt`, `revokedAt`, `revocationReason` and audit metadata are not a complete immutable event history; DENIED currently writes `revokedAt`, and emergency supersession, appointment cancellation and erasure blur semantics. Do not rewrite old logs or assert complete historical reconstruction. Tie order and stored REQUESTED/APPROVED partial index must be reconciled with all entry points.

**Migration:** existing enums already contain REQUESTED/APPROVED/DENIED/REVOKED/EXPIRED, consent IDs, scope/expiry, timestamps, partial active-pair index and audit FK; the core consent lock and scope-query fix is **not demonstrated to require a migration**. Correctly representing cancellation/supersession, decision timestamp, scope revision, durable expiry or per-document grants may need an additional status/column/event model depending on owner decisions and existing historical ambiguity. No migration is specified, created or applied; if required, document constraints/indexes, backfill/ambiguity, compatibility, retention, isolated tests and rollback before seeking separate authorization.

## 6. Real PostgreSQL concurrency verification design (not run)

Use an isolated disposable cluster and synthetic fixtures only. Start application and PostgreSQL with independent authenticated connections (operation A, revoke B, observer C); instrument test-only authorization hooks/barriers without exposing them in production builds. A must signal **after actual shared row lock and post-lock checks**, then block before protected use/commit; B invokes the real HTTP revoke. C observes actual backend PIDs and `pg_stat_activity`/`pg_locks` or `pg_blocking_pids`, state and persisted rows. Assert B is waiting on A (not just that a sleep elapsed), no revoke receipt/state committed; release A; assert A's data/write and its audit commit or rollback, then B's UPDATE and receipt commit, ordered by explicit client acknowledgements and DB visibility/ledger sequence. Prove in reverse ordering: B holds uncommitted update, A waits; after B commits A rechecks and returns denial/no sensitive bytes/clinical mutation. A request begun earlier but not yet authorized follows lock acquisition, not start time. Bound waits and fail if barrier not reached; never treat a timeout alone as proof.

Repeat both orders for record, encounter (including critical block and successful override), link mint, signed download/decrypt, and server-rendered print; authorize link before revoke then download after, which must deny. Verify response body assembled before commit but network delivery may lag. Test two authorized readers concurrently holding shared locks, simultaneous revokes (one receipt), auto-revoke, cancellation, emergency, grant/re-request, no-row/approval race, patient and doctor erasure, doctor rejection/suspension and multi-pair order. Wrong patient/doctor, unverified doctor including document endpoints, missing/pending/denied/revoked/expired, exact expiry boundary and expiry while waiting must deny with correct state; same-request approved prior to expiry may finish. No clinic model exists: wrong-clinic isolation is **not testable as a real tenant claim**; wrong-doctor/patient tests are not a substitute.

Inject audit failure after mutations and prove full clinical/revoke rollback and no success response; verify chain, exact event count and state on independent C. Test denied-audit failure policy. Terminate A's connection at pre-commit, inject statement timeout and constraint failure; prove no commit where observable, locks released and B proceeds; simulate ambiguous COMMIT disconnect and require unknown/reconciliation, not fake certainty. Force a controlled `40P01` with two independent clients and verify victim rollback, sanitized result and no unsafe automatic retry; then exercise actual application lock-order interleavings and assert no deadlock under the documented ordering. These are different tests: an artificial deadlock does not prove app ordering. Scope-canary tests above must assert SQL returned rows and safety inputs, not only filtered output. Record test counts, server/DB versions, isolation, barrier ordering, `pg_blocking_pids`, commit/receipt events and all failures/skips with no secrets or real patient data.

After approved implementation, run the specified relevant unit tests, independent-connection suite, focused HTTP and full HTTP E2E, TypeScript, ESLint, production build and `git diff --check` on isolated synthetic infrastructure; browser doctor/patient request/approve/deny/revoke/record/consultation/print regression at 320/375/390/414/768/1024/1280/1440 with evidence and explicit accessibility/device limits. Tests must pass without unexplained skips before acceptance; previous 25/25 sequential HTTP and 40 viewport samples are historical and not DW-P0 evidence.
