## Boundary inventory and paths not found

- `DELETE /api/documents/[id]` is PATIENT-only: transaction tombstones the document, deletes blob and appends `DELETE_DOC`; it is not a doctor write. Doctor-facing link and download are separately reauthorized at present but not transactionally synchronized.
- `/api/patient/fhir`, `/api/patient/print-summary`, patient record pages and patient document uploads use PATIENT role/profile. They are not doctor export routes; role/session/dependent-switch isolation still needs negative tests. `web/src/lib/fhir.ts` is a helper, not an independent doctor API. No dedicated doctor FHIR endpoint, encounter-detail GET, server PDF export or doctor document upload was found in the route scan. Encounter reads are sections of record/print, not a distinct route.
- `repo.ts` helpers and direct SQL do not authorize themselves; any newly added route, RSC, job or raw DB client using them can bypass a shared boundary. The record route comment “ONLY path” is not literal: document and server-rendered print also read clinical data. Endpoints or dashboard metadata may disclose existence, diagnosis-related content or identity independently of clinical record consent; OD-17–24 and OD-40 remain candidates for separately reviewed boundary, not downgraded blockers.
- Existing `liveConsent` evaluates REVOKED/DENIED before expiry, then clock, then other status; DB `now()` is selected with latest consent, with application `new Date()` fallback only when no row. REQUESTED is not approval; expiry is derived even if stored status stays APPROVED. `requireVerifiedDoctor` itself is a separate unlocked query. No tenant/clinic isolation model is proven.
