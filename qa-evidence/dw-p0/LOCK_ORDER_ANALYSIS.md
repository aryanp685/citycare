# DW-P0 lock order analysis

**Static code/schema-file evidence, not runtime lock observation. DW-P0-01 and DW-P0-02 OPEN / NOT ACCEPTED; all owner decisions PENDING.** This analysis covers in-repo app/schema paths found by `rg` and route inspection; deployed schema, external/direct SQL writers, actual query plans, pooler behavior and DB privileges were not inspected. No database was contacted. PostgreSQL lock compatibility and wait-for cycles below are analysis, not a demonstrated incident.

## Current transaction and reader inventory — verified from source

`web/src/lib/db.ts`: `tx` checks out a client, `BEGIN`, callback, `COMMIT`, rollback on error; no explicit isolation level (effective server default is not verified). Non-transactional `one/all/run` issue separate pool/worker-client statements; `poolQuery` can retry selected transient connection errors. `liveConsent` has no `FOR UPDATE/SHARE`, selects newest pair by `requestedAt` without tie-break, compares status and expiry using statement `now()`. Record/print and link/download each read consent then later read protected data outside one transaction. Encounter does so then starts a separate mutation transaction. All can observe stale authorization after a concurrent revoke; static reasoning, not a measured exploit.

### Other overlapping writers — current source orders

These do not grant doctor access, but their locks, snapshots and records can interact with an authorization transaction; this list is app-source inventory, not proof of a deployment-wide inventory.

- `api/patient/profile`: tx deletes patient-reported Allergy → Condition → Medication, inserts replacements, updates Patient; `PROFILE_UPDATED` audit after commit. Concurrent doctor safety reads can observe a different snapshot unless a consistent read policy is designed.
- `api/patient/photo`: pre-reads Medication; tx checks/inserts draft Medication and Notification; `MEDS_DRAFTED_FROM_PHOTO` after tx. `api/patient/medications/[id]/confirm`: separate SELECT → Medication UPDATE → separate audit. These modify safety inputs without consent locking.
- `api/patient/observations` POST/DELETE: standalone Observation insert/delete, then best-effort standalone audit. `api/patient/documents` POST: tx Document INSERT → DocumentBlob INSERT, then best-effort `UPLOAD_DOC`; shared `api/documents/[id]` DELETE: tx Document UPDATE → DocumentBlob DELETE → `DELETE_DOC` ledger. Account for document read/delete and FK order, not just consent revoke.
- `api/patient/dependents` creates User/Patient, handover tx updates User → Patient → Session/PolicyAcceptance and audits after; `api/patient/nominee` updates Patient then audits separately. `api/auth/signup` creates User plus Patient or Doctor. These identity/guardian/session changes matter if the proposed account-level gates encompass them.
- `api/patient/purge` also revokes sessions inside the erasure tx, then appends receipt separately. `api/cron/daily` calls patient/doctor erasure in separate txs and best-effort receipt; admin review notifications are after its tx. Audit policy changes must not silently rewrite this established erasure trade-off.

## Existing/missing consent row — analysis, not implemented

`schema/sql/constraints.sql` defines `one_active_consent_per_pair` on `(doctorId,patientId)` where status REQUESTED/APPROVED; expiry is **not** part of its predicate. In a correctly installed schema it enforces active stored-row uniqueness and may cause conflicting inserts to wait/fail; it does not lock an absent pair for SELECT, enforce timestamp ordering, synchronize arbitrary terminal rows, or ensure application paths recheck a changed grant. Inspect actual installation only in an authorized isolated test. New requests after terminal status create another row; concurrent record selection uses latest requestedAt with no deterministic tie-break. A selector filtering just APPROVED can misreport pending/denied/revoked, and selecting an old consent must not silently reinstate it. No claim that pure row locking alone resolves absence, replacement or bulk erasure.

**Candidate protocol (not approved or proven):** use a universal, domain-separated transaction-scoped pair gate acquired shared by readers and exclusive by all pair-changing writers, including request, patient grant/revoke, booking/cancel, auto-revoke, emergency and expiry. Pair hash collisions must only over-serialize, not change authorization. After the gate, acquire `FOR SHARE` on the authoritative existing Consent row, re-read committed status, patient/doctor, scope and expiry and compare a **fresh** `clock_timestamp()` after waiting. Missing is denied, not locked; new approval authorizes only a new properly checked operation. Hold consent lock and any relevant Doctor verification lock through authorized data retrieval/write, audit and response construction, then commit or rollback. `FOR KEY SHARE` does not conflict with ordinary non-key status updates; `FOR SHARE` does. Revocation's row UPDATE waits for holders and its receipt commits in the same transaction. Status transitions and history, pair-selection ties and emergency re-grants remain PENDING (OD-01–08, 25–33, 44–45).

**Bulk identity gate unresolved:** pair gates alone do not prevent a new pair appearing while erasure enumerates. Candidate patient/doctor-level gate acquired by *all* pair creators and erasures, with shared normal/exclusive erase modes, stable identity order and sorted pair keys; a proof must cover overlapping patient and doctor erasure, profile deletion/status changes and no-row creation. Coarse gating or an alternative may be appropriate, but has contention implications. A row that is absent cannot itself serve as a row lock. No design is accepted until actual FK/trigger paths and isolated tests establish no missed pair and no cycles.

## Proposed global ordering — hypothesis, not a demonstrated order

1. Authenticate and resolve IDs without protected content; obtain account/patient and doctor-level gates in one globally defined key order, including multi-patient/doctor erasure. If required by OD-06/08, lock/check Doctor status before pair/consent; all Doctor mutators must follow same order. Revalidate data used to choose keys after lock acquisition.
2. Acquire all pair gates in deterministic `(patientId,doctorId)` order, then all authoritative consent rows in deterministic primary-key order, taking lock modes appropriate to reader/writer. A patient revoke without an existing row must still synchronize pair if the protocol uses a pair gate. A shared gate alone is insufficient if any mutator does not participate.
3. Then acquire appointment and clinical/document rows/FK-related rows in a proven order. Avoid lock upgrades and discover IDs without retaining higher-order locks; account for current booking/cancellation and document deletion. Create complete scoped DTO / buffered bytes or perform clinical write and safety checks while the authorization remains held.
4. Append ledger **last** among locks that may be contested; account for ledger INSERT's own FK checks, notifications, and all other writes after audit. `notify` after ledger can still cause waits/cycles; prove or move operations based on full graph. `ledger_append` itself takes advisory 740110; do not merely move one visible append and assume a proof.
5. Commit before protected success; rollback on error/deadlock `40P01`, statement timeout or failure. Never replay a non-idempotent encounter automatically on an ambiguous COMMIT. A lost connection during commit can leave outcome unknown. Handle denials carefully: an audit appended then thrown in the same transaction is rolled back.

Ordering across gate classes and keys, reader/writer lock compatibility, pre-discovery race handling, max hold time and isolation level need engineering review and owner policy confirmation. Server-controlled wall-clock may move backward; lapse persistence prevents revival only *after observed lapse*, not an unobserved rollback. A signed-link download must authorize again; network transfer / a print copy already delivered cannot be revoked retroactively.

## Concrete wait-for risks to test

- **Ledger ↔ consent:** proposed protected transaction holds Consent SHARE then waits for ledger; current appointment status holds ledger advisory lock then attempts the same Consent UPDATE. Cycle possible if both conditions apply. Current clinical reader has no consent share lock, so this is a **hazard of a partial future change**, not an asserted currently observed deadlock.
- **Doctor ↔ consent:** proposed doctor-then-consent path can wait behind emergency review holding Consent then trying Doctor UPDATE; cycle possible if review needs a Doctor lock held by that path. Reorder all relevant mutators, not just protected readers.
- **Appointment ↔ consent:** cancellation/status acquire appointment before consent; erasure acquires consent before appointment. Different concurrent workflows can form a cycle depending on rows/locks; need controlled test, not assume every execution deadlocks.
- **Bulk erasure / unique index / new grants:** nonordered multi-row updates, patient/doctor erasure overlap and a concurrent insert can wait, conflict, or escape an incomplete enumeration. A partial unique index is not a bulk-erase gate.
- **Ledger FK and SQL triggers:** `schema/citycare_init.sql` defines AuditLog → Consent (`ON DELETE SET NULL`) and → User RESTRICT, Consent → Patient/Doctor RESTRICT; Appointment → Consent SET NULL; Encounter/Prescription/Medication/Document/Observation reference parent rows. Migration 0004 `DocumentBlob` → Document CASCADE. FK checks may take parent-row key-share locks, and cascading/set-null actions may acquire additional locks; exact lock interactions depend on changed columns and real schema. Audit append-only trigger (`schema/sql/constraints.sql`) rejects AuditLog UPDATE/DELETE, potentially interacting with `ON DELETE SET NULL`; do not assume consent deletion succeeds. Ledger insert after taking advisory lock can wait on FK checks when a conflicting key/delete lock exists; ordinary non-key Consent UPDATE typically permits FK key-share, so do **not** claim every audit insert blocks on every revoke. Unique index waits and FK interactions must be exercised. The hash-chain SQL serializes appends but does not itself authorize or prove metadata confidentiality. Check all migrations and deployment schema before relying on this inventory.

## Proposal V1 — concrete global lock graph (NOT IMPLEMENTED / NOT PROVEN)

This section refines and supersedes the older hypothetical order above for the proposed implementation; the current-source inventory remains historical evidence. No claim of complete deployment coverage or deadlock freedom is made until all SQL/FK/trigger paths and external writers are inventoried and independent-connection tests pass. `AUTHORIZATION_BOUNDARY_DESIGN.md` and the V1 scope/test contracts refer to this order. All 48 owner approvals remain PENDING. The global gate is intentionally conservative and is a design alternative, not authorization to add infrastructure or a table.

### A. Lock classes and exact order

All protocol participants start one dedicated READ COMMITTED transaction. Lock sets are acquired by the following classes in increasing order and held to COMMIT/ROLLBACK; no DB operation that may acquire an earlier class is allowed after entering a later one. Authenticate/validate and non-sensitive, unlocked discovery may precede `BEGIN`, but cannot return or authorize clinical content; after locks re-read and validate discovered IDs. If discovery changes, ROLLBACK, release all locks and restart a bounded number of times, never acquire an earlier class late.

1. **G — global admission/erasure gate.** Every listed participant takes a shared transaction-level advisory gate; patient or doctor bulk erasure takes the *exclusive* gate before discovering any affected pairs or rows. This global exclusivity blocks all compliant pair creation, revocation, protected operations and covered clinical writers while erasure enumerates. It simplifies cross-patient/doctor discovery at the cost of blocking unrelated patients. It does **not** control writers that bypass the protocol. Concurrent erasures serialize at G, avoiding an unknown second entity set. Patient erasure continues existing receipt policy pending OD-40.
2. **P then D — identity gates.** For every known patient ID, acquire patient gate(s) in ascending canonical ID order, then every doctor gate in ascending canonical ID order. Shared for protected operations, patient consent changes, appointment changes and patient clinical/document changes; exclusive D for doctor verification/rejection/suspension and for emergency creation (also serializes that doctor's 24-hour quota); erasure already holds G exclusive and takes affected P/D gates exclusive. If any operation needs exclusive, request it from the outset. Multiple IDs discovered for erasure are enumerated under G exclusive; no compliant writer can add a new pair during enumeration. A guardian or actor identity gate, if needed after OD-08, has to be specified here and taken in a globally fixed order before parent rows; it is not assumed implemented.
3. **R — parent rows.** Acquire in fixed table order `User → Patient → Doctor`, within table by primary-key byte order, covering audit actor, notification recipients and all relevant FK parents. For unchanged User/Patient use `FOR KEY SHARE`; if they are to be updated use `FOR UPDATE` from the start. Doctor protected/read/normal-pair paths use `FOR SHARE` and verification recheck; verification/suspension/doctor erasure use `FOR UPDATE`. Multiple required parent rows are collected before locking and pre-locked in order, including patient guardian if selected. Read status/identity after waiting. If a newly discovered parent is needed, roll back and restart rather than lock out of order. Account/session status locking beyond existing session behavior is OD-08 PENDING; this proposal does not claim session linearization.
4. **K — patient/doctor pair gates**, exclusive for any grant/request/deny/revoke/lapse/replacement/auto-revoke/emergency/review; shared for doctor read/write/print/link/download. Sort by actual lock-key order as defined below, after P/D; use the strongest required mode for all operations on a key. For a missing consent, K still exists; creators and deniers serialize, and absence means denial, never a fictitious row lock. The single active partial unique index is a second guard, not K. No row insertion/replacement outside K. For bulk erasure under exclusive G, enumerate all existing pairs after G and obtain sorted K exclusive before consent rows; no concurrent compliant creator can appear.
5. **C — consent rows**, sorted by primary key, `FOR SHARE` for authorized protected work and `FOR UPDATE` for transition/review/erase; insert under K exclusive. Select authoritative latest row for pair ordered by `requestedAt DESC, id DESC`, then lock by ID and repeat latest lookup/status/scope/patient/doctor/expiry after any wait. This deterministic tie-break is a technical proposal and changes previously unspecified tie behavior, not a historical rewrite. Never fall back to an older APPROVED row when a newer row is pending/terminal. An approval/revoke operation targets a specific ID and revalidates its patient, pair, and permitted transition under lock. A request that saw no row denies even if grant follows; a retry is a new operation.
6. **H — patient clinical-content gate(s)**, sorted by actual key, shared for record/print/link/download and exclusive for encounter creation, patient profile/medication/observation/document writes or deletions, and erasure. The coarse per-patient gate prevents covered patient clinical writers from changing rule inputs between reads and commit; it also serializes all covered writes and can be expensive. A scope plan and the fresh clock recheck must happen after potentially waiting on H: no clinical values are retrieved before successful authorization; obtain gate without querying clinical content, then re-read C/Doctor and `clock_timestamp()` before callback. This avoids claiming a check made before an H wait remains valid through expiry. This gate does not give a historical snapshot against unparticipating writers or raw DB clients.
7. **O — business/clinical rows and constraints.** Fixed order `Appointment → Allergy → Condition → Medication → Encounter → Document → DocumentBlob → LabResult → Observation → Prescription → Alert → Notification → other explicitly enumerated child rows`, within each table ascending canonical ID; take `FOR SHARE` for document metadata/blob consistency if needed, `FOR UPDATE` from outset for rows being updated/deleted. Operations creating rows must account for FK parent checks and unique index waits; new row IDs preallocated before O. Cross-table FK parent ordering must be checked against this list; if cascade requires a conflicting order, use the appropriate coarse H/G gate and refactor mutation order, not pretend the list proves safety. Reads need not row-lock all rows when H gates all applicable writers; result ordering is the scope contract, not necessarily lock order. Do not issue `UPDATE WHERE ...` over multiple rows assuming the planner acquires locks sorted: explicitly select/lock IDs in sorted order or prove another serialization mechanism. Prelock all remaining audit FK parents in R/C, and create or update notifications before L.
8. **L — ledger advisory transaction lock `740110`** taken by `ledger_append` last, after all potentially conflicting business/notification work. Audit INSERT still performs User/Consent FK checks and index/trigger work; verify parent prelocking and actual DB behavior in isolated tests. Multiple appends within one tx reuse L; after first append do not acquire new G/P/D/R/K/C/H/O locks or perform new business writes. COMMIT is the only release. A nontransactional denial audit uses a new standalone transaction with its own appropriate G/R/C/L order and no protected payload.

Advisory implementation proposal: use PostgreSQL's two-`int4` advisory key space for G/P/D/K/H, with a distinct first integer namespace for each class, and the second integer a stable hash of canonical IDs/pair with explicit domain/version encoding. The ledger's single-bigint key `740110` is a different PostgreSQL advisory key space. Hash collisions within a class are permitted only to over-serialize: calculate actual signed int keys for a whole class, coalesce duplicates to the **strongest** mode and acquire ascending numeric actual key order, not merely original ID order. No upgrade after a shared lock; otherwise collision or two simultaneous upgrades can deadlock. P/D identity lists are still sorted in canonical ID order for row locks; gate acquisition uses sorted actual keys. Namespace constants, canonicalization, hash version and collision tests must be defined consistently in code before implementation. No existing request-only key is presumed equivalent.

### C. Wait-for analysis and limits

- **Prior inversions:** current appointment status `Appointment → L → Consent` conflicts with proposed `C → Appointment → L`; refactor the whole transaction to K/C before appointment, audit last. Current patient cancel `Appointment → Consent` versus erasure `Consent → Appointment` is removed only after *all* participate in G and order; prelookup must not keep appointment row locks. Existing emergency review `Consent → Doctor` must be refactored to D/R Doctor → K/C. Current doctor erasure `Consent → Doctor` must acquire G exclusive then U parent/consent in order. Merely adding a reader share lock while leaving any writer unchanged can deadlock.
- **H and data consistency:** authorized read obtains H shared; covered patient or doctor clinical writers take H exclusive. Under READ COMMITTED, ordinary reads are separate snapshots; if every writer participates, H prevents their clinical content from changing during the read, but direct DB writers and omitted endpoints invalidate this claim. Do not silently switch to REPEATABLE READ: fixed snapshots before waits could conceal revocation; any alternative needs a new proof.
- **R/FK/unique:** parent FK KEY SHARE checks, uniqueness conflicts on active consent/appointment/other indexes, ON DELETE SET NULL/CASCADE, audit append-only trigger and L→FK work introduce implicit edges. Audit Actor/Consent parents must be acquired before L, strongest mode selected in advance. Normal non-key UPDATE and FK KEY SHARE are often compatible; key updates/deletes and unlisted trigger work need actual SQL/version testing. Audit FK `ON DELETE SET NULL` may conflict with the append-only trigger. DDL/backup maintenance, free-text patient IDs, auth sessions and external SQL require inventory; G doesn't protect writers that ignore it.
- **Deadlocks and failure:** ordering removes the *specified* inversions only if universal participation, compatible implicit FK order and predeclared sets hold. Hash collisions, cross-account unique indexes, arbitrary triggers, audit-only writers, timeout and undiscovered key changes remain counterexamples to be tested. No deadlock-freedom claim. Avoid all S→X lock upgrades (roll back and restart acquiring X if needed). Handle `40P01`, lock/statement timeout and serialization failures by rollback and generic failure; retry only a proven read-only/idempotent whole transaction with fresh authorization. Never blindly retry clinical writes or unknown COMMIT; outcome reconciliation/operation ID is unresolved OD-05 and may need separate migration approval.
- **Recheck and expiry:** after G/P/D/R/K/C/H waits, re-read verified Doctor and exact authoritative Consent under held locks, then `clock_timestamp()` once. On expiry deny even if stored status is APPROVED; equality denies. Revoke/suspension after linearization wait, expiry wall-clock itself does not. Observed durable lapse and clock rollback require OD-31–33; don't upgrade C while holding shared K/C. Roll back and re-enter a mutation transaction with K exclusive if a durable lapse event is required.
- **Contention:** G exclusive makes erasure a stop-the-world operation; H exclusive serializes all patient clinical writes and may delay reads; long document decrypt/buffering and RSC generation hold locks, L is globally serialized. Bound size, lock and statement time based on isolated measurement, consider the connection pool / proxy and fail safely. Timeouts do not prove authorization or successful revocation. This conservative design is deliberately expensive, not a performance or production-readiness claim.
