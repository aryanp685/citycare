## Shared boundary and lifecycle — proposal

`withDoctorAuthorization(viewer, patientId, action, callback)` is an architectural interface, not new code. Only a server-authenticated DOCTOR may call it, with existing same-origin/notice and session protections retained. Identity, non-sensitive input validation, and a minimal routing lookup may precede the transaction; no clinical data, sensitive document metadata or blob does. A guessed `patientId`/document/appointment must be treated as untrusted. Any discovered ID, document-to-patient relation, appointment-to-pair link and status are re-read under the final transaction/gates before use; if changed, roll back and restart discovery once within a bounded retry, otherwise deny/fail safely. Do not hold an earlier transaction's locks while rediscovering.

One dedicated PostgreSQL connection, explicit READ COMMITTED `BEGIN`, pinned UTC convention, and V1 lock order throughout. Obtain the applicable gates and Doctor row lock, then authoritative consent row lock, re-read committed data after every wait, use a separate `clock_timestamp()` sampled **after** the final authorization lock, and only then evaluate patient/doctor pair, status (`APPROVED`, not pending/denied/revoked/expired), `expiresAt > clock`, and scope/action plan. This instant is authorization linearization. A prior authorized transaction may finish while revoke/suspension waits; a request authorized after those changes commit must see them. A time-expired grant cannot authorize another operation, even if stored status remains APPROVED. An operation authorized before expiry may finish after it per current milestone target; formal owner confirmation OD-01/02 remains PENDING. No cache of consent/verification verdict crosses transactions.

The callback receives a transaction-only opaque capability with exact patient/doctor/consent/scope and scoped-query interface; never expose a reusable consent verdict that allows unrestricted repo queries. Use scoped SQL and rule inputs described in scope contract, build immutable output (and, for downloads, decrypted byte buffer) inside the transaction; run all required state writes/notification and success audit before commit; do not emit any protected byte or success prior to an unambiguous COMMIT. Only transmit the immutable result after commit. React server components must not lazily run protected queries after callback or stream sensitive content before commit. Lock release is COMMIT/ROLLBACK; a failed operation gives no protected success. Network transfer can continue after commit, and copies already delivered/printed cannot be recalled. An explicit safety/clinical choice remains pending; a scope that lacks approved safe-write prerequisites refuses the write rather than silently fetching hidden facts.

Relationship is not interchangeable with consent: a valid approved grant for this exact doctor/patient establishes the clinical-sharing relationship, including a separately approved emergency override; an appointment by itself is not authority. Request-access still needs its appointment relationship. Existing server page's appointment **or any historical consent** relationship gate is not a live clinical grant; identity/guardian metadata, directory, appointment reason and activity outside clinical scope remain OD-17–23/40, with original blocker labels unchanged. A new arbitrary emergency patient must not require a pre-existing appointment in a way that silently removes break-glass; identification/eligibility policy is OD-44/45 PENDING. No clinic tenant model exists; do not claim clinic isolation.

**Denial and errors:** use a uniform externally safe not-found/forbidden mapping pending OD-24; no patient/document existence, hidden facts, SQL text or status details in error/log. Preserve internal semantic classification REQUESTED, DENIED, REVOKED, EXPIRED and absent without calling a denial a revocation. Proposed denied audit is a minimal committed denial event (never throw after appending inside the same transaction and thereby erase it); if the security audit fails, still return generic denial, record a non-PHI operational alert, and never allow access. Proposed successful protected operation audit is mandatory in the same transaction; audit failure rolls back and returns generic 5xx with no protected output. This is an explicit technical recommendation pending OD-34–40, not an approved policy; existing purge's erasure-first receipt exception is separate, not silently rewritten.

**Uncertain outcome:** a definite pre-COMMIT failure → rollback and safe retriable failure, no automatic non-idempotent replay. Connection loss during/after COMMIT → `outcome_unknown`, never promise rollback or success and never replay write, mint or audit automatically. Reconcile via an approved durable operation identifier/idempotency mechanism or support-visible receipt/audit when available; this proposal does not assume one exists or authorize schema. Retrying a read is a new operation and reauthorizes; duplicate mutation handling requires a separate approved design. No PHI in operational errors. Timeout/latency budgets are engineering measurements, not arbitrary owner-selected values (OD-04/05).

## Link expiry, replay and audit — detailed proposal

Current `storage.ts` signs document ID + user ID + expiry; TTL is 60 seconds and signature is reusable during its validity. Proposed default remains a short UID-bound link with the same expiry and **multiple uses allowed only while each GET independently reauthorizes**. An expired signature always denies even with a live grant; whether same link can be used after revoke and a subsequent new grant is an explicit replay-policy decision (owner/security OD-03/15/44): choose between binding to the original grant ID/version and rejecting across replacement, or accepting under a separately rechecked new grant. Recommendation for implementation review is grant-bound rejection, not approved; absence of grant ID in current signature requires a compatible token change, not necessarily migration. Do not silently assume single-use: true single-use requires atomic durable redemption state and separate design/migration review. Verify signature again after waits if TTL has passed before authorization; check DB consent time after locks and signature time using a defined trusted source. Each successful use gets a distinct event; repeated failed attempts must not leak metadata.

The lock spans authorization → row identity/non-deleted recheck → authorized metadata/blob → decrypt → buffer/header → mandatory audit → commit. Link mint and download are distinct events; old `DOWNLOAD_DOC` events cannot be retroactively relabeled as actual delivery. Doctor suspended or revoke committed before lock acquisition means deny; if operation already authorized, revoke/suspension waits to commit and response bytes may transmit later. A previously minted URL is not itself sufficient, a previously downloaded/printed file cannot be recalled, and no audit can prove delivery to or deletion from an external client.
