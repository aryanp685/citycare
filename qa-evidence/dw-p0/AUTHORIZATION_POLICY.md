# DW-P0 authorization policy — implementation target

A doctor clinical operation begins a PostgreSQL READ COMMITTED transaction and locks the matching authoritative approved consent row with `FOR SHARE` before rechecking status, patient/doctor identity and expiry on the database wall clock. The lock stays held through the scoped clinical queries, response construction and relevant audit/write, until commit or rollback. Concurrent authorized readers may share the lock. Revocation, denial, expiry transitions and other updates acquire conflicting row locks: revocation waits for operations already holding the share lock, and subsequent operations must check a post-revocation row state rather than reuse a pre-transaction verdict. Requests that start before revocation but acquire their authorization only afterwards must be denied. Bytes already delivered or a response already prepared before revocation cannot be recalled. A signed document link is not authority: download separately reauthorizes and holds its own lock through decryption and response construction; network transmission may finish after transaction commit.

The intended lock order is consent row before clinical rows / document blobs / audit ledger; audit must be acquired last. Appointment auto-revocation currently appends an audit before updating consent and must be reordered to avoid a ledger-to-consent inversion. Any other transaction taking ledger then consent must be audited. PostgreSQL chooses deadlock victims and transactions roll back; absent a proven safe idempotent retry scheme, return a safe error rather than replay clinical writes automatically. Expiry is checked after acquiring the lock with `clock_timestamp()` (not transaction-start `now()`); an operation authorized while consent is valid can finish under its lock even if wall-clock expiry occurs before commit.

Scope is a server-side authorization boundary: do not read all clinical sections then filter. Determine permitted sections/encounter IDs first on the locked transaction, query only those rows, and run safety rules only against that authorized result. Summary and last-N retain existing explicitly shared allergy/condition/medication safety facts; specific-condition retains those safety facts under current model but must not load unrelated encounter/lab/prescription content. Specific-documents and malformed/unknown scopes fail closed. If essential clinical safety facts are absent from the granted scope, do not silently supplement them. Patient-origin access is governed separately by patient ownership, not a doctor consent.

This policy is a target, not evidence that implementation or tests are complete. No clinic role/tenant model currently exists; wrong-clinic behavior must not be claimed tested. The documented locks cannot control raw database clients which bypass application authorization.

## Unresolved design and review gates

This is not yet an implementation-ready proof. In particular, an absent matching row cannot itself be locked; concurrent creation/replacement and the partial uniqueness constraint need explicit analysis, as do latest-status reporting and expiry. Lock ordering must cover every consent mutation, including appointment completion, emergency overrides and erasure, plus audit failure and transaction rollback. A simple query restricted to `APPROVED` would collapse pending, denied, revoked and missing states and would not satisfy audit semantics. The effect of concurrent doctor verification changes also needs review. The exact set of safety facts authorized by each scope needs owner confirmation; failing closed for unsafe writes is preferable to silently broadening scope. The scope query must preserve existing selection/limit semantics and avoid leaking unrelated text while selecting condition-linked encounters.

No application change implementing this policy is included in this milestone. An experimental partial implementation was removed before handoff because it did not cover all protected paths or pass TypeScript; it must not be mistaken for a fix. A full independent-connection test harness must exercise the real application endpoints and transaction barriers, not just demonstrate generic PostgreSQL row locks.
