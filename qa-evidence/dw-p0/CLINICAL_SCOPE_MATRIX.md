# DW-P0 clinical scope matrix

**Static evidence and proposed design only. All clinical scope and safety choices below are PENDING qualified clinical and owner/privacy review; DW-P0-01 and DW-P0-02 remain OPEN / NOT ACCEPTED.** Current behavior is not an approved consent contract, comprehensive safety check, diagnosis or prescribing guidance. No actual patient data or runtime/DB test was used. Source: current `web/src/lib/{repo,consent,rules,validate}.ts`, doctor record/encounter/document routes, doctor print page and `schema/citycare_init.sql`.

## How to read the current matrix

`recordSections(patientId)` currently retrieves **all** eight sections into the application before `applyScope`; the “visible” column means only the current in-memory result, not pre-query isolation. For `record` and doctor print, `scopedRecord` uses this pattern. Encounter safety calls **full `recordSections` directly regardless of scope**. `GrantSchema` offers FULL_RECORD, SUMMARY_ONLY, LAST_N_ENCOUNTERS, SPECIFIC_CONDITION; `conditionName` is optional even for SPECIFIC_CONDITION; N is optional 1–50 for API grants. Doctor request UI/API supports only FULL/SUMMARY/LAST_N. Schema has SPECIFIC_DOCUMENTS and `documentIds`, but current grant validation/filter/download do not implement selected-document access. Patient ownership routes are separate and must not be broken by changing the doctor query.

| Scope | Current visible record/print sections **after loading all** | Linked records, document access and safety inputs | Review decisions — all PENDING |
|---|---|---|---|

Limits applied before filtering can yield fewer selected records than a filter-then-limit query; tests must explicitly decide whether to preserve existing source semantics or approve a change. Ordering ties, fields and nulls need review. Any future query that selects condition matches must distinguish a PostgreSQL predicate inspecting candidate diagnosis text from returning out-of-scope rows to application/rules; stricter “DB never evaluates restricted text” requires another design and explicit decision.

## Safety processing and restricted-write prerequisites

**Current evidence:** `toRuleRecord` maps active allergy allergen/severity, confirmed active medication names, labs name/value/unit/ranges/date and encounters follow-up/diagnosis. `runAllRules` checks drug–allergy conflict, abnormal labs, follow-up due and stale HbA1c; declared NSAID set/interaction type does not establish a general drug-interaction rule. Doctor-proposed items are added for encounter checks. A CRITICAL allergy conflict returns detailed 422 `alerts` unless an override reason is supplied; write otherwise persists all generated alerts (with evidence), a count, and audit metadata including drug names/override/conflict titles. Narrow consent is **not** applied to encounter safety inputs. A permitted fact may legitimately cause a warning; a hidden fact must not be retrieved or used simply to make a more complete warning. No claim that rules are clinically complete or reviewed.

**Proposed, not implemented:** build a server-side scope plan from the transaction-protected consent, retrieve only permitted rows/columns into the application, pass only those values plus clinician-proposed input to safety, digest, print and alerts, and preserve source values for permitted data. If qualified reviewers determine a particular write requires safety facts not in scope, refuse generically and request appropriate permission; do not silently widen and do not claim safe prescribing from incomplete inputs. The safety facts essential to each write, permitted scope matrix, behavior for unavailable data, override UX and clinical review are **PENDING** OD-10–16. This is not a clinical recommendation and does not authorize deleting safety checks.

## Leakage surfaces — proposed non-disclosure property, not currently proven

For every restriction and denial, out-of-scope content must not be returned, serialized, logged, stored in a doctor-visible artifact, or exposed by derived facts. Examples using only synthetic marker `HIDDEN-ONLY-42`:

- **Warnings and errors:** allergy/drug conflict titles and messages/evidence; abnormal lab name/value/range/date; follow-up diagnosis/date; stale-test warning; response counts and 422 alerts. Current encounter uses full clinical data, so these are plausible leakage channels; no new runtime disclosure was demonstrated here.
- **Responses/metadata:** digest and abnormal lab summaries, scope notes, encounter counts, IDs, checksums, MIME, titles, filenames, content-disposition/content-length, timestamps, demographic/ABHA/guardian, appointment reason, own-visit date, notifications, status distinctions/existence and URL; client state or cache can retain previously delivered content.
- **Print and export:** entire server-rendered HTML and React Flight payload, hidden print nodes, print/PDF text and images; a no-longer-authorized newly requested page must not contain forbidden facts. A copy already delivered before revocation cannot be recalled. Print is not a new authenticated server request.
- **Logs and audit:** API exception handler logs errors; DB exception text, query parameters, traces, alert evidence, `CREATE_ENCOUNTER` medication/override payload, `PRESCRIBE_OVERRIDE` conflict titles, notification text and audit metadata need minimization; a generic response alone does not prove log privacy. Audit policy including denial failure remains PENDING OD-34–40.

## Retrieval contract V1 — explicit proposal, not approved or implemented

This section refines the design above; it does not describe current enforcement. The shared authorization/transaction and V1 gate/lock order are defined in `AUTHORIZATION_BOUNDARY_DESIGN.md` and `LOCK_ORDER_ANALYSIS.md`. **No scope plan is enabled until owner/privacy approves the exact field matrix and a qualified clinician approves safety prerequisites.** If the plan is absent, unsupported or invalid, the proposed operation denies *before retrieving clinical fields*, with generic error and safely committed minimal denial evidence subject to audit policy. This is a proposed fail-closed branch, not a decision already made; approval OD-09–16/47–48 PENDING. Patient-only APIs keep separate ownership semantics.

### A. Candidate column catalog and shared SQL rules

All values remain original source values; rule-derived flags do not replace them. These are **maximum candidate projections**, not approved disclosure. The owner/privacy decision may select a strict subset; the prepared SQL template must project only the selected authorized columns rather than fetch then redact. If the policy matrix or required columns are undecided, deny rather than use this catalog as implicit approval. Joins and internal filtering use IDs/fields in DB; only selected rows and allowed output columns may leave the DB. Internal IDs/predicate fields must not be serialized unless explicitly permitted.

| Code | Candidate table and output columns; mandatory predicates |
|---|---|
| A | `Allergy(id, allergen, severity, reaction)` with `patientId=:P AND isActive=true`; `ORDER BY allergen ASC,id ASC`. No limit currently; resource cap requires separate decision. |
| C | `Condition(id,name,status,icd10)` with `patientId=:P AND status='ACTIVE'`; `ORDER BY name ASC,id ASC`. No limit currently. |
| M | `Medication(id,name,dosage,frequency,notes)` with `patientId=:P AND isActive=true`; `ORDER BY name ASC,id ASC`; `notes` access and DRAFT visibility separately PENDING; rules exclude notes beginning `DRAFT:`. No limit currently. |
| E | `Encounter(id,encounterDate,type,chiefComplaint,diagnosisText,diagnosisCode,advice,followUpOn)` plus treating `Doctor.fullName AS doctor`; `patientId=:P`; `ORDER BY encounterDate DESC,id DESC`; cap 50. |
| L | `LabResult(id,testName,value,unit,refRangeLow,refRangeHigh,takenOn,documentId)` plus `Document.encounterId`; join `Document` by lab document ID and require `Document.patientId=:P AND NOT Document.isDeleted`; `ORDER BY takenOn DESC NULLS LAST, LabResult.id DESC`; base cap 200. documentId and encounterId are themselves sensitive and only projected if approved. |
| O | `Observation(id,name,category,valueNum,unit,refLow,refHigh,takenOn,encounterId)` where `patientId=:P AND valueNum IS NOT NULL AND takenOn IS NOT NULL`; `ORDER BY name ASC,takenOn ASC,id ASC`; base cap 1000. |
| Rx | `Prescription(id,issuedOn,items,notes,encounterId)` plus `Doctor.fullName AS doctor`, inner join `Encounter` on encounterId with `Encounter.patientId=:P`; `ORDER BY issuedOn DESC,Prescription.id DESC`; base cap 50. Null-linked prescription is not in current join. |
| D | `Document(id,title,type,source,issuedOn,ocrStatus)` where `patientId=:P AND NOT isDeleted`; `ORDER BY createdAt DESC,id DESC`; base cap 50. Download-specific internal projection is `patientId,isDeleted,title,mimeType,encryptionIv,checksumSha256` and `DocumentBlob.data` only after separate authorization. `createdAt` may be used in DB ordering without being disclosed. |
| P/G | `Patient(id,fullName,dateOfBirth,gender,bloodGroup,city,abhaId,guardianPatientId,guardianRelation)` and guardian `Patient.fullName` via guardianPatientId. `id=:P`; may project only individually approved fields; guardian ID/relation/name, ABHA, date and city are **not automatically in any scope**. Name/age/gender/blood group, currently used in digest, are also OD-09 PENDING. If essential patient identifier is not authorized, deny that response rather than infer permission. |

All ordering uses a stable deterministic ID tie-breaker, which changes previously unspecified tie cases and needs approval/test. Naive timestamps use the existing UTC convention; verify session timezone. Cap policies beyond current ones are OD-12/13/47 pending. For compatibility with existing outputs, V1's candidate **base-limit-first** contract is defined below: construct deterministic ID-only CTEs under `:P` and each original base predicate/order/limit, then apply scope membership in SQL, then project authorized row fields. No nonselected row or its clinical contents is returned to the application. `MATERIALIZED` or equivalent query shape must preserve the intended pre-filter caps; execution planner may internally inspect/index/order candidate fields, so it does not prove DB-level non-evaluation. This avoids silently switching to scope-filter-first top-K, which could return more/different rows than today's filtering-after-limit. Owner/privacy/clinical approval OD-12–14 is needed for either behavior, including tie changes.

Definitions in the same authorized transaction and after V1 recheck:
- `E50 = SELECT id FROM Encounter WHERE patientId=:P ORDER BY encounterDate DESC,id DESC LIMIT 50`. Only its IDs are used in SQL. `EN = SELECT id FROM E50 in that same order LIMIT :N`; `:N` is valid integer 1–50. Candidate legacy compatibility: NULL → 3; any other invalid value denies, never slices with malformed N. Owner/clinician must explicitly accept the default.
- `L200`, `O1000`, `Rx50`, `D50` are ID-only base CTEs produced using each table's A-column predicates/order/cap in the catalog. Selection predicates below apply to **those IDs** inside DB before the final output projection; not every matching row in the database is necessarily selected because base limit comes first.
- `EC = E50` IDs for which `(position(lower(:condition) in lower(coalesce(diagnosisText,''))) > 0 OR position(lower(:condition) in lower(coalesce(chiefComplaint,''))) > 0)`. `:condition` must be trimmed, nonempty and meet the approved validation bounds; empty/null/malformed denies. Use parameterized text literal matching (not interpolated LIKE wildcards). Case-folding/collation equivalence to JS and Unicode semantics require tests and an owner-reviewed choice; database predicates **evaluate candidate diagnosis/complaint** but do not return nonmatching text/rows to Node/rules. If privacy requires even DB not to evaluate nonmatching content, EC is not viable and scope must deny until a separately approved model/index exists.

### C. Pre-query denial, warning and output contract

After V1 locks and post-wait clock/status check, reject missing/not-approved/expired/revoked grants, unknown scope, missing approval matrix, invalid N, missing/invalid condition, invalid selected IDs and absent write prerequisites before any clinical SQL. Do not use absent data as evidence of a negative clinical fact. Externally return a generic, consistent no-access/need-review message subject to OD-24; internally retain truthful state (not denied-as-revoked), with metadata-minimized audit. For a valid scope, only warnings computed from allowed A/M/L/E + explicitly provided proposed input may enter 422/JSON, Alert rows or notification. Otherwise return generic refusal without hidden identifiers, values, counts, exceptions or evidence. No notification/audit/log/print/HTML/Flight/JSON/header may contain out-of-scope fields, derived values, document title/bytes or distinguishing counts, including when SQL or audit fails. Minimal audit fields and denial-outage policy remain OD-34–40 PENDING. Warnings within scope must remain source-faithful; no suppressed safety check may be represented as completed. `P0_ACCEPTANCE_TEST_SPEC.md` defines synthetic evidence required.
